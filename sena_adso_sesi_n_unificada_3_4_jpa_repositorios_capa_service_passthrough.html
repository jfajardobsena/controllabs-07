2. Fundamentos de ORM, JPA e Hibernate

Cómo Java se comunica con PostgreSQL sin escribir sentencias SQL repetitivas.

La Incompatibilidad de Paradigmas (Object-Relational Impedance Mismatch)

¿Por qué necesitamos un traductor entre Java y SQL?

En Java trabajamos con Clases, Objetos, Referencias y Tipos Complejos. En PostgreSQL guardamos datos en Tablas, Filas y Claves Foráneas (FK). Un ORM traduce automáticamente nuestras acciones en Java (`repository.save(loan)`) a sentencias SQL nativas (`INSERT INTO loans...`).

📜 JPA (Jakarta Persistence API)

Es la especificación estándar (las reglas y anotaciones como @Entity, @Table, @Id). No ejecuta código por sí sola.

⚙️ Hibernate ORM

Es el motor real que implementa JPA en Spring Boot. Lee tus anotaciones, construye el SQL optimizado para PostgreSQL y administra la conexión.

3. ¿Por qué Configuramos `application.properties`?

4. Mapeo de Entidades JPA (`controllabs.sql`) & Anotaciones Clave

Cómo traducimos cada tabla, tipo de dato, Enum y clave foránea de PostgreSQL a clases Java.

Anotaciones Esenciales en una Entidad JPA

@Entity + @Table

@Entity hace que JPA administre la clase como entidad; @Table(name = "...") indica la tabla concreta a la que corresponde.

@Id + @GeneratedValue

@Id identifica la clave primaria. @GeneratedValue delega la generación: UUID para usuarios/salas e IDENTITY para préstamos.

@Column

Configura el mapeo de un campo: nombre de columna, longitud, nulabilidad, unicidad y si puede actualizarse. Se usa para hacer explícitas las reglas del esquema.

@Enumerated(EnumType.STRING)

Guarda el nombre del enum en vez de su posición numérica, evitando que reordenar constantes cambie el significado de datos existentes.

@ManyToOne + @JoinColumn

Modela una FK hacia otra entidad; @JoinColumn especifica el nombre de la columna y FetchType.LAZY posterga la carga relacionada.

@Getter, @Setter, @NoArgsConstructor

Anotaciones de Lombok, no de JPA: generan accesores y un constructor vacío que JPA necesita para materializar entidades, reduciendo código repetido.

¿Por qué las anotaciones van en la Entidad? La entidad es el modelo persistente: sus anotaciones describen a Hibernate cómo convertir objetos Java en tablas, columnas, claves y relaciones. No pongas @RestController ni @Service aquí; pertenecen a otras capas.

Otras anotaciones JPA que puedes necesitar en una Entity

No se agregan todas por defecto: elige según el esquema y el comportamiento que necesite el dominio.

@SequenceGenerator

Nombra y configura una secuencia de la base de datos. Se usa junto con @GeneratedValue(strategy = SEQUENCE, generator = "...") cuando PostgreSQL o el esquema existente asigna IDs mediante una secuencia. No se combina como estrategia activa con UUID o IDENTITY.

@Version

Marca una columna de versión para control de concurrencia optimista. Hibernate detecta si otra transacción modificó la fila y evita sobrescribir silenciosamente ese cambio.

@Transient

Excluye un campo de la persistencia JPA. Úsala para un valor calculado temporal; no para datos que deban consultarse o guardarse en una columna.

@PrePersist / @PreUpdate

Indican métodos de ciclo de vida que se ejecutan antes de insertar o actualizar. Son útiles para inicializar marcas de tiempo; usa updatable = false en la columna de creación si no debe cambiar después.

@OneToMany(mappedBy = "...")

Representa el lado inverso de una relación uno-a-muchos, por ejemplo una sala con sus equipos. mappedBy apunta al atributo room de EquipmentEntity; la FK se mantiene en el lado @ManyToOne.

@OneToOne / @ManyToMany

Modelan relaciones uno-a-uno o muchos-a-muchos cuando el dominio realmente las exige. La relación muchos-a-muchos suele necesitar una tabla de unión; si esa unión tiene datos propios, es preferible convertirla en una entidad intermedia.

Regla práctica: mantén las entidades enfocadas en persistencia. Evita poner @Data de Lombok en entidades con relaciones: su equals, hashCode o toString generados pueden recorrer relaciones lazy o producir ciclos. Para enviar JSON, convierte la entidad a un DTO.

import jakarta.persistence.*;
import lombok.*;
import java.time.OffsetDateTime;
import java.util.UUID;

@Entity
@Table(name = "users")
@Getter @Setter
@NoArgsConstructor @AllArgsConstructor
public class UserEntity {

    @Id

    private UUID id;

    @Column(nullable = false, unique = true)
    private String email;

    @Column(nullable = false, length = 150)
    private String nombre;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private UserRole rol;

    @Column(nullable = false)
    private Boolean activo = true;

    @Column(name = "created_at", nullable = false, updatable = false)
    private OffsetDateTime createdAt = OffsetDateTime.now();

    public enum UserRole {
        ADMIN, GUARDA, INSTRUCTOR
    }
}

package com.sena.controllabs.entity;

@Table(name = "loans")

5. Capa Repository: Repositorios CRUD Base

Cada interfaz hereda de `JpaRepository<Entidad, ID>` y utiliza solo las operaciones CRUD que Spring Data proporciona.

1. Genéricos <Entidad, TipoID>

Al escribir extends JpaRepository<UserEntity, UUID>, Spring proporciona los métodos CRUD (`save`, `findAll`, `findById`, `deleteById`) sin SQL ni métodos de búsqueda personalizados.

2. ¿Qué es Optional<T>?

Es una "caja segura" de Java que puede contener un resultado o estar vacía. findById(id) devuelve un Optional<T> para representar que un registro puede no existir.

Referencia: anotaciones y convenciones del Repository

@Repository marca la interfaz como componente de acceso a datos y permite que Spring la detecte. Spring Data crea la implementación automáticamente; en muchos proyectos Spring la detección de interfaces JPA hace que esta anotación sea opcional, pero aquí se muestra explícitamente.

extends JpaRepository<Entidad, ID> no es una anotación: hereda operaciones CRUD y paginación, y le dice a Spring Data qué entidad y tipo de identificador administrar.

En esta guía no se declaran métodos findBy..., @Query, @Param, derived queries ni JPQL. Cuando se requiera buscar por otros campos, esa decisión se agregará en otra etapa; por ahora cada Repository conserva solo el CRUD heredado.

El Repository no lleva @Service ni conoce HTTP. El acceso a los datos se invoca desde la capa Service.

6. Capa Service (`@Service`): Puente Passthrough hacia el Repositorio

Creamos la capa intermedia de servicios delegando directamente al repositorio, dejando lista la arquitectura limpia sin lógica compleja aún.

¿Por qué crear el Servicio si hoy solo llama al Repositorio?

El Controller nunca debe hablar directamente con la Base de Datos (`Repository`).

Al implementar el patrón Interfaz (`*Service`) + Implementación (`*ServiceImpl`) como un puente limpio (Passthrough), desacoplamos el protocolo HTTP del acceso a datos. En la próxima sesión agregaremos aquí las reglas de negocio del SENA (validaciones de disponibilidad de equipos, cambios de estado y firma) sin tener que modificar una sola línea de nuestros Controladores.

Controller (@RestController) Service (@Service Passthrough) Repository (JpaRepository) PostgreSQL

Referencia: anotaciones en la capa Service

@Service registra la clase de implementación como un bean de Spring y comunica su responsabilidad: coordinar casos de uso y reglas de negocio. Aquí se usa en *ServiceImpl, no en la interfaz.

@Override es una anotación de Java, no de Spring: el compilador confirma que cada método implementa o sobrescribe uno declarado en la interfaz.

La inyección por constructor mostrada en los ejemplos no necesita anotación: Spring detecta el constructor único y provee el Repository. Hace explícita la dependencia y facilita las pruebas. En esta sesión el servicio solo delega; las reglas de negocio se agregarán aquí más adelante.

7. Solución Simplificada: Conversión DTO ↔ Entity en los propios Records

Para evitar crear archivos o carpetas `mapper/` adicionales, aprovechamos los Java 17 Records agregando métodos de conversión directos (`toEntity()` y `fromEntity(...)`).

Arquitectura Limpia y Sin Archivos Extra

Cada DTO sabe cómo convertirse a Entidad (Request) o cómo construirse desde una Entidad (Response).

El Controller recibe un RoomCreateRequest y llama a su método .toEntity() para obtener la RoomEntity que necesita el Servicio. Cuando el Servicio devuelve la entidad guardada, llamamos al método estático RoomResponse.fromEntity(...). ¡Cero clases extra y cero dependencias!

JSON Request → requestDto.toEntity() → Service (Entity) → Repository (Entity) → ResponseDto.fromEntity()

Referencia: anotaciones de validación en los DTOs

@NotBlank rechaza texto nulo, vacío o compuesto solo por espacios; se aplica a los campos de texto obligatorios.

@NotNull rechaza valores ausentes o nulos. En totalPcs es necesaria porque es un Integer nullable.

@Min(1) establece el mínimo permitido para la cantidad de PCs. Es una restricción numérica y complementa a @NotNull.

Las restricciones declaran qué datos acepta el request. Por sí solas no validan nada: el Controller debe activar la validación con @Valid. Los DTOs de respuesta no llevan estas restricciones porque contienen datos ya procesados para enviar al cliente.

Otras anotaciones útiles para DTOs

Escoge las restricciones que describan el contrato de cada request. No es necesario añadirlas todas a cada campo.

@Email

Comprueba que un texto tenga formato de correo. Si el campo también es obligatorio, combínala con @NotBlank: @Email @NotBlank String email.

@Size(min = 2, max = 100)

Limita la longitud de cadenas o el tamaño de colecciones. No exige que el valor exista; combínala con @NotBlank o @NotNull si es requerido.

@Pattern(regexp = "...")

Exige que una cadena coincida con una expresión regular, por ejemplo un código con formato específico. Añade un mensaje claro y evita patrones más complejos de lo necesario.

@Positive / @PositiveOrZero

Valida números mayores que cero o mayores/iguales a cero. Igual que @Min, no rechaza por sí sola el valor nulo; combínala con @NotNull si hace falta.

@Past / @Future

Restringe fechas a un instante anterior o posterior al actual. Para fechas opcionales, la mayoría de estas restricciones permite null; agrega @NotNull cuando sea obligatorio.

@NotEmpty

Rechaza nulo y vacío en cadenas, colecciones o arreglos, pero una cadena de espacios puede pasar. Para texto obligatorio normalmente conviene @NotBlank.

@Valid

También sirve en una propiedad anidada o en cada elemento de una lista para activar la validación recursiva: List<@Valid ItemRequest>.

@JsonProperty / @JsonIgnore

De Jackson, no de Bean Validation: permiten fijar el nombre JSON de una propiedad o excluirla de la serialización. Úsalas solo si el contrato JSON requiere un nombre distinto o el campo no debe exponerse.

Constraint personalizada

Para reglas entre varios campos (por ejemplo, fecha final posterior a fecha inicial), crea una anotación propia con un validador de clase. No fuerces esa regla dentro de una expresión regular.

📁 com/sena/controllabs/dto/RoomCreateRequest.java Incluye .toEntity() 
package com.sena.controllabs.dto;

import com.sena.controllabs.entity.RoomEntity;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;

public record RoomCreateRequest(
        @NotBlank(message = "El nombre es obligatorio")
        String name,

        @NotBlank(message = "El bloque es obligatorio")
        String locationBlock,

        @NotNull(message = "La capacidad de PCs es obligatoria")
        @Min(value = 1, message = "Mínimo 1 PC")
        Integer totalPcs
) {
    // Convierte este DTO directamente en una Entidad JPA
    public RoomEntity toEntity() {
        RoomEntity entity = new RoomEntity();
        entity.setNombre(this.name);
        entity.setBloque(this.locationBlock);
        entity.setCapacidadPcs(this.totalPcs);
        entity.setEstado(RoomEntity.RoomStatus.OPERATIVO);
        return entity;
    }
}

    public static RoomResponse fromEntity(RoomEntity entity) {
        return new RoomResponse(
                entity.getId(),
                entity.getNombre(),
                entity.getBloque(),
                entity.getCapacidadPcs(),
                entity.getEstado().name()
        );
    }
}

8. Conexión Final: Controller Ultra Limpio (DTOs + Service Passthrough)

El `@RestController` solo inyecta el `Service` y utiliza los métodos directos de los Records (`toEntity` y `fromEntity`).

Referencia: anotaciones en la capa Controller

@RestController registra el componente web y combina @Controller con @ResponseBody: los valores devueltos se serializan como JSON en vez de buscar una vista.

@RequestMapping("/rooms") define el prefijo común de las rutas de esta clase. Junto al prefijo global /api/v1 forma la URL completa.

@GetMapping, @PostMapping y @DeleteMapping asocian métodos HTTP con métodos Java, manteniendo el Controller responsable de HTTP y no de acceder a JPA.

@PathVariable toma un valor de la ruta (por ejemplo, el UUID en /rooms/{id}); @RequestParam toma un parámetro de consulta opcional como ?block=A.

@RequestBody convierte el cuerpo JSON del request al DTO correspondiente. @Valid ejecuta las restricciones de Bean Validation declaradas en ese DTO.

ResponseEntity no es una anotación: permite expresar explícitamente el estado HTTP y el cuerpo de la respuesta, como 201 Created o 204 No Content.

📁 com/sena/controllabs/controller/RoomController.java (Sin Mapper Extra) Solo inyecta RoomService 
package com.sena.controllabs.controller;

import com.sena.controllabs.dto.RoomCreateRequest;
import com.sena.controllabs.dto.RoomResponse;
import com.sena.controllabs.entity.RoomEntity;
import com.sena.controllabs.service.RoomService;
import jakarta.validation.Valid;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import java.util.List;

@RestController
@RequestMapping("/rooms")
public class RoomController {

    private final RoomService roomService;

    // Solo inyectamos el Servicio, ¡el código queda súper limpio!
    public RoomController(RoomService roomService) {
        this.roomService = roomService;
    }

    @GetMapping
    public ResponseEntity<List<RoomResponse>> getAllRooms() {
        List<RoomResponse> responseList = roomService.findAll()
                .stream()
                .map(RoomResponse::fromEntity) // Conversión directa con referencia a método
                .toList();

        return ResponseEntity.ok(responseList);
    }

    @PostMapping
    public ResponseEntity<RoomResponse> createRoom(@Valid @RequestBody RoomCreateRequest requestDto) {
        // 1. Convertimos DTO -> Entity con .toEntity() y guardamos en el Service
        RoomEntity savedEntity = roomService.save(requestDto.toEntity());

        // 2. Convertimos Entity -> DTO con RoomResponse.fromEntity(...) y respondemos
        return ResponseEntity.status(HttpStatus.CREATED)
                .body(RoomResponse.fromEntity(savedEntity));
    }
}
